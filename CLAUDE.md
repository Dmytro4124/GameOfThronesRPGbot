# Telegram Game of Thrones RPG Bot - Core Developer Guidelines

## 1. Архітектура та Стек
- **Мова:** Python 3
- **Асинхронність:** `asyncio` (КРИТИЧНО: всі виклики до Gemini API та Google Sheets є синхронними під капотом і ПОВИННІ загортатися в `asyncio.to_thread()`).
- **База даних:** Google Sheets (бібліотека `gspread`).
- ШІ (Гібридний роутинг на Gemma): Проєкт використовує жорстко розділені моделі для балансу швидкості та якості в межах лімітів (15K TPM): gemma-3-4b-it — для логіки, парсингу та математики (Worker, GM_Logic). gemma-3-27b-it — ВИКЛЮЧНО для художнього тексту (Narrator). gemini-embedding-2-preview — для RAG та векторного пошуку.

## 2. Карта Проекту (Де що лежить)
- `core/mechanics.py`: Вся ігрова математика, обчислення наслідків, валідація дій (ToT, Roll-over 2d50).
- `core/engine.py`: Головний ігровий цикл, генерація сторітелінгу (GM), оркестрація викликів, фонове збереження.
- `core/ai_client.py`: Ініціалізація Gemini, критичні функції парсингу (`clean_and_parse_json`).
- `database/operations.py`: Взаємодія з Google Sheets та локальною векторною базою (RAG на базі `numpy`).
- `core/prompts.py`: Єдине місце зберігання всіх системних промптів (реалізовані як функції-будівники).
- `bot/handlers.py`: Telegram-маршрутизація, захист від спаму, керування UX (тайм-аути).

## 3. Гібридна 3-Агентна Система (Data Flow)

### Головний ігровий цикл у core/engine.py суворо розділений на 3 послідовні кроки. ЗАБОРОНЕНО зливати їх в один.

### Робота з ШІ та Промптами    
- Worker (Mechanics): gemma-3-4b-it. Аналізує інпут, визначає навички, повертає механічні наміри.
- GM_Logic (State Manager): gemma-3-27b-it. Рахує зміни світу. Повертає ВИКЛЮЧНО сухий JSON (npc_updates, suggested_actions, director_notes).
- Narrator (Writer): gemma-3-27b-it. Отримує масив фактів director_notes та генерує ЧИСТИЙ художній текст. Не має жодних JSON-інструкцій.

## 4. Жорсткі правила кодування (НЕ ПОРУШУВАТИ) 

### Робота з ШІ та Промптами    
- Всі нові промпти мають додаватися виключно у core/prompts.py як функції. Ніяких inline f-strings в логіці.
- Теги `<system>`, `<player_state>`, `<world_context>`, `<mechanical_verdict>` є обов'язковим архітектурним стандартом. Не видаляй їх при рефакторингу промптів.
- Ніколи не змінюй структуру ключів JSON у промптах (наприклад, step1_tot_brainstorming, director_notes, npc_updates), якщо розробник не дав прямої команди. Парсери зав'язані на ці ключі.

### Робота з Даними
- Не використовуй стандартні ORM. Всі операції з базою йдуть через `database/operations.py`.
- Завжди використовуй функцію `safe_int()` для роботи зі значеннями з профілю гравця, оскільки Google Sheets може повертати пусті рядки або текст замість чисел.
- Не ігноруй перевірки на NullPointerException при роботі з інвентарем (`profile.get("Інвентар", "")`).

## 5. Базові Ігрові Механіки (Для загального розуміння)
- **Roll-over система:** Використовується `2d50` + Навичка. (Перевага/Недолік реалізовані через `max()`/`min()`).
- **Скілпоїнти:** Нараховуються ВИКЛЮЧНО у двох випадках: успішне проходження тренування (через `process_training_request`) або викид кубика строго понад 95 (Критичний успіх).
- **Енергія:** Базовий ресурс (0-100). При падінні <= 0 гравець втрачає свідомість — це жорсткий overrides (перехоплення) будь-якої дії.

## 6. Маршрутизація (Skills)
Перед модифікацією складних вузлів, звертайся до вузькоспеціалізованих правил. Запитай у розробника наявність файлів у `.claude/skills/`:
- Якщо редагуєш боївку або кубики -> запитай правила механік.
- Якщо редагуєш RAG або роботу з NPC -> запитай правила бази даних.
